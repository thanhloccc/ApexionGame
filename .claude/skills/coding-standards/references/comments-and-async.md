# Comments, async, logging and conditional compilation

`CODING-CONVENTIONS.md` §5 and §12.

## 1. The comment rule

> **Do not write comments or XML docs unless the Project Owner asks for them.**
> **Do not touch existing comments** in files you edit. Leave them exactly as they are.

This covers `//`, `/* */`, section dividers, and every XML doc tag.

This is the house rule most likely to be violated by instinct, because adding an explanatory comment
feels like care in most codebases. Here it is not asked for, and adding one to a file you are editing
for another reason is scope creep in the diff.

**Always allowed, no permission needed:**

| Allowed | Note |
|---|---|
| `// SAFETY:` above an `unsafe` block | **Required**, not optional — see §5 below |
| License headers and attribution on vendored or ported files | Must be preserved when moving files |
| `<auto-generated>` markers from build tools | Never hand-edit the file either |
| `#region` / `#endregion` | — |

**Do not touch existing comments** means exactly that: not reformatting them, not correcting their
grammar, not deleting one that looks stale. A stale comment is someone else's decision to make.

### When XML docs *are* requested

Keep them short. `<summary>` says what the type does; `<remarks>` covers thread safety and
constraints. **Never repeat what the code already says.**

```csharp
/// <summary>
/// A dictionary that stores its values in a contiguous array, so the values
/// can be iterated directly as an array, without an enumerator.
/// </summary>
/// <remarks>
/// Not thread-safe.
/// </remarks>
public partial struct ArrayMapNative<TKey, TValue> : ...
```

Note what that example does: it explains the *consequence* of a design choice — why you would pick
this type — and states a constraint a caller cannot see. It does not say "a dictionary that maps
keys to values".

### The one place a comment is required by another rule

A **measured** performance decision that looks wrong gets a comment saying why — otherwise the next
person "fixes" it and reintroduces the problem. Same for a deliberate regression. That is
`midcore-perf-budget`'s rule, and it overrides the default silence here because the alternative is
losing the measurement.

## 2. Async

- Async method names end with **`Async`**.
- **`CancellationToken token = default` is always the last parameter.** Pass the token to every async
  call inside.
- **Check the token at the start of significant work**:
  `if (token.IsCancellationRequested) { return ...; }`.
- **Always re-throw `OperationCanceledException`. Never swallow it.** Swallowing turns a cancelled
  operation into a silently successful one, and the caller cannot tell.
- Async code supports both UniTask and Unity `Awaitable` through the `UNITASK` define and the
  `UnityTask` alias pattern — the alias set-up is `encosy-tower/references/recipes.md`.

```csharp
public static async Awaitable WaitUntilAsync(
      this MonoBehaviour target
    , Func<bool> predicate
    , CancellationToken token = default
)
```

- `IDisposable` classes use the `Dispose(bool disposing)` + `GC.SuppressFinalize(this)` pattern.

## 3. Logging

- **Log through the project's logging module** (`StaticDevLogger`, `DevLogger`, `Logger`, …).
  **Never call `UnityEngine.Debug.Log*` directly.**
- Log wrappers carry `[HideInCallstack, StackTraceHidden]` so they stay out of user stack traces:

```csharp
[HideInCallstack, StackTraceHidden, MethodImpl(MethodImplOptions.AggressiveInlining)]
public void LogInfo(object message)
{
    StaticDevLogger.LogInfo(message);
}
```

- Dev-only logging goes through the `Dev` loggers — they compile away in release builds.
- **Standalone logging methods are cold paths** — annotate `[MethodImpl(NoInlining)]`
  (`members-and-attributes.md` §6).

The trap worth naming: a log call that formats its message **before** checking whether logging is
enabled pays the formatting cost always, including in release. It is invisible in review and shows
up as per-frame allocation — see `midcore-perf-budget/references/allocation-audit.md`.

## 4. Conditional compilation

- **Guard async or platform-specific code at the file level**
  (`#if UNITASK || UNITY_6000_0_OR_NEWER`), not statement by statement.
- Define internal compile symbols at the top of the files that use them.
- **Prefer `[Conditional("SYMBOL")]` on a method over wrapping every call site in `#if`.** One
  declaration instead of N places to forget.
- Platform-specific type aliases go at namespace scope.

Whether a symbol is actually visible inside a given assembly is an assembly concern, and the failure
is silent — see `midcore-assembly-architecture/references/feature-flags.md` §2.

## 5. `unsafe`

Every `unsafe` block gets a `// SAFETY:` comment **directly above it**, explaining why *this
specific* operation is sound — not a generic sentence pasted everywhere.

Order is: check → `// SAFETY:` → `unsafe` block. Full rules on native and unsafe containers:
`encosy-tower/references/collections-and-math.md`.
