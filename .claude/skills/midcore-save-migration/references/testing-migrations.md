# Testing migrations

Without this file's practices, everything else in this skill is aspiration. A migration is only known
to work against a **real file from the real old format** — not against what you believe that format
was.

## 1. Golden fixtures

> **Keep a real save file from every shipped version, in the repo, forever.**

A golden fixture is a save produced by an actual build of that version, committed alongside the tests.
Not generated by current code — that only proves current code agrees with itself.

**How to capture one**, at the moment a version ships:

1. Build the version being shipped.
2. Play far enough to populate the data meaningfully — not a fresh save. Some progress, some
   inventory, some collections with several entries, at least one optional/absent field exercised.
3. Take the resulting file, commit it under its version:
   `fixtures/save/v4/progress.sav`, `fixtures/save/v4/settings.sav`.
4. Alongside it, commit a **plain-text description of what that save contains**: level 12, 3400 gold,
   these seven items, this quest at this step. That is the ground truth every later assertion checks
   against.

**Never regenerate a fixture.** The moment it is regenerated by current code, it stops being evidence
of the old format and becomes a copy of the new one. If a fixture seems wrong, the answer is to find
out why — not to refresh it.

**Never delete one.** Old versions are exactly what the chain must still handle.

If the format is encrypted, commit a fixture that the test harness can decrypt — either a
test-key-encrypted copy or a documented way to read it. A fixture nothing can open is not a fixture.

## 2. The test matrix

The mistake is testing only N-1 → N. Players skip versions.

```
for every shipped version V in save.shipped_versions:
    load fixture(V) → migrate to current → assert semantic content
```

Every shipped version, every run. This is a loop, not a list of hand-written tests — adding a version
should extend coverage automatically, because the test that is hand-added is the test that gets
forgotten.

Also assert:

| Case | Expected |
|---|---|
| Current-version file | Loads with **no** migration run |
| Version newer than current | Handled deliberately — refuse, do not "try anyway" |
| Truncated / corrupt file | Fails cleanly; original preserved; no wipe |
| Empty file | Same |
| Missing optional fields | Documented defaults applied |
| Unknown extra fields | Tolerated, not fatal |

## 3. Assert on semantic content, not bytes

A byte comparison fails on any serializer change, field reordering, or whitespace difference — so it
gets disabled, and coverage goes with it.

Assert what the data **means**:

```
migrated = migrate(fixture_v4)

assert migrated.Level          == 12          // from the fixture's description file
assert migrated.Gold           == 3400
assert migrated.Items.Count    == 7
assert migrated.Items[SwordId] == 1
assert migrated.Quest          == (chapter 2, step 3)
assert migrated.Version        == CURRENT
```

The values come from the description committed with the fixture. This is why the description matters:
it is the independent record of what that save contained, written when it was captured.

**Assert on counts and totals, not just presence.** A re-key migration that silently drops three of
seven items passes any "the collection exists" check.

## 4. Property tests worth having

Beyond fixtures, a few invariants that should hold for **every** migration:

- **Determinism** — migrating the same input twice yields identical output. Catches accidental clock
  or randomness use.
- **Idempotence at the boundary** — migrating an already-current save is a no-op, not a second
  application of the last step.
- **No total loss** — for any fixture, currency and item counts after migration are ≥ before, unless
  the migration explicitly and intentionally reduces them.
- **Chain composition** — `migrate(v3 → v5)` equals `migrate(migrate(v3 → v4) → v5)`. Catches a step
  that quietly depends on being run in a particular combination.

## 5. Testing the recovery paths

The paths that only run when something has already gone wrong are the least tested and the most
consequential. Test them deliberately:

| Scenario | Assert |
|---|---|
| Interrupt between write and swap | Original still loads; no partial file left behind |
| Temporary file fails to parse | Original untouched; error reported |
| One blob of several fails | Configured policy applied (all-or-nothing vs per-blob) |
| Backup exists and primary is corrupt | Backup loads; player informed |
| Both corrupt | Fails visibly; **file preserved**; no new game started |
| Disk full mid-write | Original intact |

The last row of that table — *no new game started* — is the single most important assertion in this
skill. Write it as an explicit test, with a name that says so, so nobody deletes it as redundant.

## 6. Before shipping a migration

- [ ] Golden fixture from the previous version committed, with its description
- [ ] Every shipped version → current passes
- [ ] Current version loads with no migration run
- [ ] Corrupt and truncated inputs fail cleanly, file preserved, no wipe
- [ ] Interrupted migration leaves the original loadable
- [ ] Determinism and no-total-loss properties hold
- [ ] Ran against a file from a **real build**, not a synthesized one
- [ ] Profile's `save.shipped_versions` updated with the new version

That last item is what makes the next person's matrix correct. Skipping it means the next migration
is tested against a shorter history than actually exists.
