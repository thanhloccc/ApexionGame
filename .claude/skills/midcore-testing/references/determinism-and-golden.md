# Determinism, golden runs, and flakiness

## 1. Determinism is a prerequisite, not a feature

A simulation that cannot be replayed cannot be tested beyond the shallowest level, cannot produce a
golden run, and cannot have a bug report reproduced from a seed.

Four sources of non-determinism, in the order they cause trouble:

| Source | Fix |
|---|---|
| **Unseeded randomness** | One explicitly seeded generator per simulation, seed stored with the run |
| **Variable timestep** | Simulate on a fixed step; decouple it from render rate |
| **Wall-clock time** | Inject time; logic never reads the system clock directly |
| **Unstable iteration order** | Iterate collections whose order is defined, or sort before iterating |

The last one is the quiet one. A hash-ordered collection can iterate differently between runs,
platforms, or versions, and the resulting bug appears months later on one platform only.

### Shared randomness is the classic trap

One global generator shared by simulation and cosmetics means a change to a particle effect alters
every subsequent gameplay roll. Separate streams: one for simulation, one for everything that does
not affect outcomes. Only the simulation stream needs to be deterministic — but it needs to be
absolutely.

### Floating point across platforms

Identical float operations can differ between architectures and compiler settings. For most games
this does not matter. It matters if replays or golden runs must validate across platforms — in which
case either accept a tolerance, or move the parts that must match exactly to integer/fixed-point.

Decide this deliberately and write it down. Discovering it when a golden run fails only on CI is an
expensive way to learn it.

## 2. Golden runs

Drive a deterministic simulation for N steps from a fixed seed and initial state; compare the result
against a recorded trace.

**Strengths:** enormous coverage per test. Catches emergent interaction bugs that no targeted test
would have thought to check.
**Weakness:** a failure says "step 4137 differs" and needs work to interpret.

### Recording

1. Fix the seed and the initial state; commit both.
2. Run N steps, capturing a **summary per step** — not the whole world. Positions, key state values,
   a hash of the significant state.
3. Commit the trace with a plain-language description of the scenario it represents.
4. Choose N so it runs in seconds. A golden run too slow to run always is a golden run that does not
   run.

**Capture summaries, not full snapshots.** A full snapshot makes every trivial addition a trace
change, and traces stop being reviewed.

### Updating a golden — the discipline that matters

A golden failing means one of two things, and confusing them destroys the test's value:

1. **A real regression.** Fix the code.
2. **An intended behaviour change.** Update the trace.

The danger is that updating is one command and always makes the failure go away. It becomes reflex,
and a real regression gets rubber-stamped.

So:

- **Never update a golden in the same change that made it fail without saying so.** State that the
  trace was updated and why, in the commit message.
- **Diff the trace before accepting it.** If the change is broader than the code change would
  explain, that is a regression wearing an update's clothes.
- **Never auto-update in CI.** Ever.
- **Re-record from a clean build**, not from a working tree with unrelated changes in it.

## 3. Flakiness

> A flaky test is worse than no test.

It trains everyone to re-run and move on, and eventually a real failure is re-run past. One flaky
test in a suite devalues the whole suite's signal.

Common causes, in order of frequency:

| Cause | Fix |
|---|---|
| Real time / frame-count dependence | Inject time; drive frames explicitly |
| Order-dependent tests sharing state | Full reset between tests; never rely on run order |
| Unstable collection iteration | Sort before asserting |
| Async work not awaited | Await it; never sleep-and-hope |
| Timeouts tuned to one machine | Widen substantially, or remove the timing assertion |
| Leftover files or state from a previous run | Isolate per run; clean up in teardown |

**Policy:** when a test is identified as flaky, fix it or delete it — within the same change if
possible. Do not mark it ignored "for now"; ignored tests are deleted tests with extra steps, and
they leave the impression that coverage exists.

Never make a test pass by retrying it. A retry hides the non-determinism, and the non-determinism is
usually also in the code under test.

## 4. Fixtures and isolation

- **Each test starts from a known state.** No dependence on what ran before.
- **Fixtures are committed data, not generated by the code under test** — the same principle as
  golden saves (`midcore-save-migration`).
- **No shared mutable static state between tests**, or run order becomes part of the contract.
- **Clean up files, even on failure.** A test that leaves state behind makes the *next* test flaky,
  and that one gets blamed.
